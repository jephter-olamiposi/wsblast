# Importing a browser session

`wsblast import` turns a session recorded in the browser into a scenario:
the messages one WebSocket connection sent, in order, with the pauses the
user took between them. Load-test the traffic your app really sends,
without writing the script by hand.

```bash
wsblast import session.har -o chat.yaml
wsblast --scenario chat.yaml
```

It is part of the default build (Cargo feature `scenario`).

## 1. Recording the session

Chrome and Edge record WebSocket frames in the HAR files they export:

1. Open DevTools (F12) and its **Network** panel before the page opens its
   WebSocket connection, or reload the page with the panel open.
2. Use the app as a user would.
3. Export the requests as a HAR file: the panel's export button, or the
   request list's context menu. Recent versions offer a sanitized export,
   without cookies and authorization headers, which is all the import
   needs.

The file holds every request of the page; the import reads only the
WebSocket connections, from each entry's `_webSocketMessages`. A HAR may
hold cookies, tokens and message contents: treat it as a secret, and keep
it out of the repository.

## 2. Options

| Option | Default | Description |
| :--- | :--- | :--- |
| `FILE.har` | | The HAR file. |
| `-o, --output FILE` | stdout | Where to write the scenario. |
| `--url TEXT` | | Import the connection whose URL contains `TEXT`. |
| `--index N` | the connection that sent the most | Import the `N`th matching connection, from 1. When the HAR has more than one, the import lists them. |
| `-c, --connections N` | `10` | Connections of the generated phase. |
| `-d, --duration D` | `1m` | Duration of the generated phase. |
| `--max-wait D` | `10s` | The longest pause kept; a longer one is shortened to it. |
| `--no-waits` | off | Leave every pause out. |

Edit the file afterwards like any scenario ([docs/scenarios.md](scenarios.md)):
add phases, stages, SLOs, `expect` checks or `{{data.COLUMN}}` templates.

## 3. What the scenario holds

Every text message the browser sent becomes a `Send` action, and a run of
the same message is one `Send` with a `count`. A pause of a millisecond or
more before a message becomes a `Wait`:

- When every message got a reply before the next one, the scenario runs in
  echo mode, where each `Send` waits for its reply; the pause is the
  user's think time, from the reply to the next message.
- Otherwise it runs in stream mode, which sends without waiting; the pause
  is the time from one message to the next. The import says how many
  messages had no reply.

The file starts with comments: the command that runs it, and what the
import left out. It is parsed and validated as `--scenario` would before
it is written, so a scenario the import writes always loads.

```yaml
# Generated by wsblast import from session.har.
# Run it with: wsblast --scenario FILE
version: '1.0'
target: wss://chat.example.com/ws
metadata:
  name: Recorded session (chat.example.com)
  description: 'Imported from session.har by wsblast import: 3 messages of one connection'
phases:
- name: recorded
  connections: 10
  duration: 1m
  actions:
  - type: Send
    payload: '{"op":"join","room":"lobby"}'
  - type: Wait
    duration: 500ms
  - type: Send
    payload: '{"op":"say","text":"hello"}'
    count: 2
```

## 4. Socket.IO

A Socket.IO connection (its URL has an `EIO` query, or the server's first
frame is an Engine.IO open packet) becomes a Socket.IO scenario:

- Engine.IO packets (pings, the open packet) and namespace connects are
  left out; `--mode socketio` sends its own.
- The argument of each event the browser emitted is a `Send`. A Socket.IO
  scenario emits one event name, so the import keeps the most frequent
  event and names the ones it left out.
- The command it prints carries `--mode socketio`, `--sio-event`, and
  `--sio-namespace` and `--sio-version 2` when they apply. The target
  drops the Engine.IO query, which `--mode socketio` adds.

```text
Wrote chat.yaml: 120 messages to wss://rt.example.com/socket.io/
Note: a Socket.IO scenario emits one event; imported 'say', the most frequent, and left out 'typing' in /chat (14)
Run it with: wsblast --scenario chat.yaml --mode socketio --sio-event say --sio-namespace /chat
```

## 5. Credentials and what is left out

- **Header values are not copied.** When the recorded handshake sent
  `Cookie` or `Authorization`, the import says so; pass the values with
  `-H 'Cookie: ...'`, or a fresh token with `--auth-type` (see
  [docs/ci.md](ci.md)).
- **Socket.IO auth objects are not copied.** The import names the keys of
  the recorded one; pass it with `--sio-auth`, or per connection with
  `{{data.COLUMN}}` ([docs/socketio.md, section 1.1](socketio.md#11-a-credential-per-connection)).
- **Binary messages are left out**, since scenario payloads are text; the
  import counts them.
- **Replies are not checked.** Add `expect` to an action to check them
  ([docs/templates.md, section 3](templates.md#3-values-from-replies-and-reply-checks)).
- **Values that change per session**, such as a session id the server
  handed out, are sent as recorded. Replace them with a `capture` and
  `{{NAME}}` in the scenario.
